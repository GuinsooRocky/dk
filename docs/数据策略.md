# DK 数据策略（v1）

> 对应产品战略 §8.4 / GUARD-7。说清楚 v1 在你这台 Mac 上**存什么、存哪、怎么清**。
> 多用户产品里，访客"零安装零账号"也意味着"零同意"——所以要把数据真相摆明。

## v1 存什么

| 数据 | 内容 | 在哪 | 生命周期 |
|---|---|---|---|
| 内存统计 | `last_text`（最近一条入站 ≤120 字）、按用户调用计数、总数 | hub 进程内存 | **重启即清**；也可在设置「清除历史」手动清 |
| 诊断日志 | 转发记录，含入站文本 `text[:80]` 片段 | `<work_dir>/.logs/*.log`（hub.log / telegram.log / feishu_app.log / wecom_ws.log） | 随文件增长；不自动轮转 |
| 会话记忆 | claude session 复用映射（不存消息原文，只存 session id 关联） | `core/threads.py` 的 SQLite | 持久，重启不丢 |

## v1 明确**不**做

- **不持久化每条消息文本到盘**：`last_text` 只在内存深度 1，重启即失。将来做 v2 SQLite stats（战略 §9）时，明确**不落 `text` 列**。
- 不做云端同步、不外传任何对话内容（Hub 绑 `127.0.0.1`，只本机）。

## 怎么清

- **设置 →「清除历史」**：清空内存统计（`POST /stats/clear`）。诊断日志不在此动（运行中进程占着句柄，UI 触发删不干净）。
- **诊断日志**：要清就停掉后端后，把 `<work_dir>/.logs/` 下的 `*.log` **移到废纸篓**（`~/.Trash`，可恢复）——**绝不 `rm`**（遵全局 no-auto-delete / trash-not-rm 立场）。

## 访客知情

- 加人（菜单栏「谁能用」点加入）前会弹授权告知，含"TA 发的消息会留在你这台 Mac 上（日志/统计）"。这是访客对"消息落在别人盘上"的唯一知情点，不可省。
