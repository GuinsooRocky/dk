# 循环工程八原则 —— 骨架级铁律

> 这不是「建议」，是 2026-07 用 soliloquy 两条自主跑批线（loop / graph）连着跑几天、
> 翻车又修好之后留下来的账。每一条底下的「为什么」都是真翻过的车，不是假想。
>
> **谁该读**：从 `ralph/` 这套骨架长出新 loop 的人。开工前通读一遍，
> 每条对照自己的 `loop.sh` / `PROMPT.md` 自查一次，能省掉一整晚的空转和一次账本丢任务。
>
> 每条三段式：**规则**（一句话）→ **为什么**（翻过的车）→ **骨架里怎么落**（具体动哪个文件）。

---

## ① 收工信号只认专用输出通道，绝不 grep 混流日志

**规则**：判断「agent 说完事了没有」只能读一个专门写结论的文件或退出码，
绝不去 grep 那条把 prompt、思考、工具输出全混在一起的主日志。

**为什么**：codex exec 会把你喂进去的 prompt 原样回显进 stdout。
于是主日志里天然就有一份 prompt 全文，而 prompt 里必然写着哨兵字面量
（"干完打印 ALL DONE"这种）。驱动 `grep -q 'ALL DONE' 主日志` 第一轮就命中——
agent 一件事没干，loop 当场宣布收工退出。这个假阳性最恶心的地方在于它**看起来完全正常**：
日志有内容、退出码 0、收工提示打印得漂漂亮亮，只有回头数 commit 才发现一笔都没有。

**骨架里怎么落**：
- 驱动调 agent 时带最终回复的独立输出参数（codex 是 `--output-last-message <file>`），
  哨兵**只**读那个文件；主日志只用来给人看。
- 每轮开跑前先删掉上一轮的那个文件，防残留误触发（`rm -f "$LAST_MSG"`）。
- 哨兵是两条缺一不可：专用通道里的字面量 + 账本状态（`fix_plan` 里真没 `- [ ]` 了）。
  只有一条成立就当没收工，宁可多跑一轮。
- 本仓 `loop.sh:36` 现在是 grep `fix_plan.md`——那是账本文件不是混流日志，合规；
  但只要哪天改成 grep `ralph/loop.log`，这条就破了。

## ② 账本是第一公民：清单条目只能被完成，不能消失

**规则**：任务清单里的每一条，终态只有「完成 / 卡住跳过 / 还没做」三种，
**没有「不见了」这一种**。驱动每批开跑前后都要拿 manifest 对一次账。

**为什么**：agent 在改 `fix_plan.md` 时会顺手「整理格式」，一次改写就能把几条待办
悄悄合并掉或删掉。下一轮全新 context 的 agent 根本不知道曾经有过这几条，
loop 于是心满意足地报告「全部完成」收工。等人回头翻 manifest 才发现，
声称做完的 32 件里实际只落地了 27 件——而且分不清是哪 5 件，因为证据本身被删了。

**骨架里怎么落**：
- 开批时冻结一份 `batch-manifest.json`：`{batchId, taskIds[], startSha, branch}`，
  **只读，agent 一律不许改**。
- 加一个对账闸（`check-ledger.sh` 这类）：manifest 里每个 taskId 在 `fix_plan.md` 里
  必须**有且仅有一个**状态标记；数量对不上直接红、拒绝继续跑。
- `fix_plan.md` 标题维护一行声明计数（"已完成 N 项，剩 M 项"），
  对账闸拿它跟实际 grep 出来的行数比——声明和实际打架就是账本被动过的信号。
- 收官时跑 `close-batch.sh` 再对一次账，并把 manifest 归档进 `archive/`。

---

## ③ 驱动的每个判断都要落盘，不许丢 /dev/null

**规则**：驱动做的每一个决定——为什么停机、为什么重试、为什么熔断、这轮闸是绿是红——
都要带时间戳写进一个专门的状态日志，**任何 `>/dev/null 2>&1` 都不许吞掉判断依据**。

**为什么**：出事的时候人只有两个信息源：跑批线还活着没有、它现在在干嘛。
驱动把检查输出全扔 `/dev/null` 之后，这两个都答不上来。
实际发生的是：跑批线空转了 6 分钟，日志里只有一行行「重试中」，
既看不出闸红在哪条测试，也看不出它到底重试了几次——
owner 只能去翻 1.5MB 的混流日志逐行找，找了半小时才定位到是同一条 flaky 测试在反复红。
**日志不是给机器看的，是给凌晨三点被叫醒的人看的。**

**骨架里怎么落**：
- 单独开一个 `logs/runner-status.log`，只写驱动自己的判断，一行一条：
  时间 + 事件（batch-start / gate-red / retry / backoff / abort）+ 原因 + 关键数值。
  它跟 agent 的混流输出物理分开，人扫一眼就知道发生了什么。
- 检查脚本可以 `>/dev/null` 掉正常输出，但**失败分支必须把 stderr 抄进状态日志**再退出。
- 熔断/停机时把原因同时打到终端和状态日志，措辞要能直接回答「我现在该干嘛」。

## ④ 恢复路径要便宜：resume 不许重复跑全量测试

**规则**：中断后续跑的入口，代价必须显著低于从头跑一遍；
尤其不许在 resume 时无条件重跑整仓全量测试。

**为什么**：全量闸跑一次 5800 条测试要好几分钟。resume 每次都先跑一遍全量，
结果就是「恢复」比「干活」还贵——监工每 2 分钟触发一次 resume，
每次白烧一遍全量闸，一整晚下来一件活没干成，额度和 CPU 全喂给了重复验证。
恢复越贵，人就越倾向于不恢复而是推倒重来，那批做到一半的工作就全废了。

**骨架里怎么落**：
- 状态全落磁盘（`fix_plan` + manifest + git），resume 只需读文件重建上下文，不需要重放历史。
- resume 默认只跑**增量闸**（本轮碰过的文件相关的检查）；全量闸只在批收口时跑一次。
- 把「上批跑到哪」记进 manifest（`lastTaskId` / `lastSha`），resume 从那接着走，
  不从 taskIds[0] 重扫。
- 检查本身分层：秒级的结构断言（本仓 `smoke_test.py` 就是）每轮跑，
  分钟级的全量套件按批跑。

## ⑤ 空转熔断用滑动窗口，不用「一成功就归零」的连续计数

**规则**：判断 loop 是不是在空转，看的是**最近 N 轮里有多少轮真的推进了账本**，
不是「连续失败几次」——因为连续计数会被任何一次无关的成功清零。

**为什么**：用 `FAIL_STREAK++ / 成功就 =0` 这种连续计数，遇到「一轮红一轮绿交替」
的情形永远熔不了断：每次 streak 刚要到阈值就被一次绿归零，
loop 可以这样欢快地跳踢踏舞跳到天亮，而账本一件没动。
真正要抓的信号从来不是「连着失败」，是「一段时间内没有净进展」。

**骨架里怎么落**：
- 维护一个长度 N（默认 10）的滑动窗口，记每轮结束时账本的完成数。
  窗口首尾之差 == 0 → 这 N 轮零净进展 → 熔断退出并告警。
- 熔断信息要说清「最近 N 轮完成数一直是 X」，人一眼看出是卡死不是慢。
- 轮数上限（本仓 `loop.sh` 的 `MAX`）保留，但它是最后一道保险，不是主判据——
  上限只防跑太久，滑动窗口才防空转。

## ⑥ 监工必须指数退避 + 失败次数上限 + 告警，不许固定间隔无限硬撞

**规则**：任何「发现死了就拉起来」的看门进程，重试间隔必须翻倍增长（封顶），
连续失败到上限就**停止自动续跑**并醒目告警，绝不固定间隔无限重试。

**为什么**：监工原本是 `dead → sleep 120 → resume → || true → 循环`。
闸只要红着（flaky 或真红），它就每 2.5 分钟白烧一遍整仓测试，
永远起不来新批，而且**一声不吭**。跑了几个小时，日志涨到 1.5MB，
owner 完全不知道它在空转——因为「还在重试」和「已经彻底跑不起来了」长得一模一样。
无限重试的本质是把「我搞不定」这个事实藏起来。

**骨架里怎么落**：
- `BACKOFF=$RETRY_DELAY`，每失败一次 `BACKOFF=$((BACKOFF*2))`，封顶 `BACKOFF_MAX`（默认 900s）。
- `FAIL_STREAK` 到 `FAIL_MAX`（默认 6）→ 停止自动续跑，打醒目告警 + 发系统通知，
  把控制权交回给人。
- 每次退避都写状态日志（见原则③），写清第几次、退避多久、上次红在哪。
- `|| true` 是这条的头号敌人：它把失败伪装成成功。要吞错误就得同时记账。

## ⑦ 换引擎（claude ↔ codex）必须过能力差异清单

**规则**：把驱动从一个 agent CLI 换到另一个，不是改一行命令的事——
必须逐项核对三件事：**回显行为、能不能 spawn 子 agent、沙箱可写边界**。

**为什么**：以为 codex 是 claude 的等价替换，直接把命令换掉，然后连撞三个坑：
① 回显——codex 把 prompt 打回 stdout，收工哨兵当场假阳性（就是原则①那车）；
② 子 agent——驱动里派子 agent 并行干活的设计在 codex 下直接不成立，
   任务规模的切分假设跟着全废；
③ 沙箱——codex 默认沙箱挡写 `.git`，agent 一 commit 就失败，
   而失败信息埋在混流日志里，表现成「跑了一晚上什么都没提交」。
这三条随便哪一条都能让一整晚白跑，而且症状都不指向真因。

**骨架里怎么落**：换引擎前照着这张表逐格填，填不出来的先去实测：

| 能力项 | 要问清的 | 影响到骨架的哪里 |
|---|---|---|
| 回显行为 | prompt 会不会进 stdout？有没有只出最终回复的参数？ | 收工哨兵（原则①） |
| 子 agent | 能不能 spawn 子 agent 并行？ | 每轮任务粒度、批大小 |
| 沙箱边界 | 哪些路径可写？`.git` 索引能不能动？网络通不通？ | commit 方式（原则⑧）、依赖安装 |
| 权限旗标 | 跳过确认的参数叫什么？ | 驱动调用行 |
| 退出码 | 失败是非 0 还是永远 0？ | 重试与熔断判据 |
| 超时 | 单轮有没有硬上限？超时怎么表现？ | 监工的存活判据 |

先拿一个「改一个字 + commit」的最小任务实跑一轮，六格全验过了再喂真 backlog。

## ⑧ 沙箱挡住 agent 提交时，约定它写 commit message 文件、驱动代交

**规则**：agent 因沙箱写不了 git 索引时，正确解法是
**agent 把 commit message 写进约定文件、驱动读文件代为提交**，
绝不是驱动来一发 `git add -A` 兜底。

**为什么**：`git add -A` 看着救了场，实际上把语义全丢了——
一笔提交裹进本轮改动、上轮残留、agent 的临时文件、半成品，
message 只能写成「ralph: auto commit」。等到要 review 或要回滚某一件时，
根本拆不开是哪笔改了什么、为什么改。**丢语义比不提交更贵**：
不提交至少改动还在工作区看得见，裹一起提交是把证据搅烂了。

**骨架里怎么落**：
- 约定文件：agent 每轮把 message 写进 `<loop_dir>/.iter-commit-msg`（首行 subject，
  正文带 `验证：` / `风险：` / `Loop-Task: <任务ID>`）。
- 驱动在闸绿之后校验这个文件：不存在 or 缺必填段 or `Loop-Task` 对不上本轮任务 →
  **保留现场、不提交**、报错退出。宁可留个脏工作区让人处理，也不产无语义 commit。
- 提交只 add agent 本轮实际碰过的文件（从 `git status --porcelain` 逐个取，
  排除 `.iter-commit-msg` 自己），`git commit -F <约定文件>`，提交成功后删掉它。
- 本仓 `PROMPT.md` 第 5 步「绝不 `git add -A`」是同一条铁律的 agent 侧表述，
  这里补的是驱动侧：驱动也不许。
